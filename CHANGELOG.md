# Changelog

## [Unreleased]

### Behavior changes

These changes are visible to OSC clients.

- Electromagnetic brake (STEP400, STEP800): the brake of each motor follows a new state machine with six states, readable with `/getBrakeStatus`. Changes for a motor with the brake enabled:
  - `/activate 1` while the brake is released does nothing. It sent a hard stop, which stopped a turning motor abruptly.
  - `/activate 1` releases the brake only if a status read after the command shows the driver energized. If the driver stays HiZ (e.g. no motor power), the brake stays engaged and `/error/command BrakeReleaseFailed motorID` is sent. Before, the brake was released after `brakeTransitionDuration` in any case.
  - `/activate 1` during the deceleration of `/softHiZ` (or `/activate 0`) cancels the engaging and keeps the brake released; the deceleration goes on. Before, it stopped the motor with a hard stop, and the brake still engaged when the motor stopped.
  - `/activate 0` on a turning motor decelerates it and engages the brake when it has stopped, like `/softHiZ`. It engaged the brake without stopping the motor.
  - `/softHiZ` and `/activate 0` on a stopped motor engage the brake at the next status read (up to 5 ms later). The stop is now judged on a status read after the command.
  - After `/free`, a stop of the motor no longer engages the brake (when `/free` was sent during the deceleration of `/softHiZ`).
  - After `/free`, a motion command (`/run`, `/move`, `/goTo`, ...) is executed and the motor returns to the released (energized) state. `/activate 1` does the same. `/activate 0`, `/softHiZ` and `/hardHiZ` after `/free` engage the brake at once (the motor is already HiZ).
  - A motion command during the deceleration of `/softHiZ` or `/activate 0` cancels the engaging; the brake stays released. Before, the brake engaged when the motor stopped later.
  - `/softStop`, `/hardStop` and `/enableServoMode 0` while the brake is engaged or after `/free` (motor HiZ) do nothing. They energized the motor, and the brake state was left engaged, so `/activate 0` and `/hardHiZ` could not make the motor HiZ again.
  - `/enableServoMode 1` and `/homing` while the brake is not released reply `/error/command BrakeEngaged motorID` and do nothing. `/enableServoMode 1` energized and moved the motor with the brake engaged; `/homing` set the homing state although it did not start.
  - When the driver goes HiZ by itself while the brake is released (overcurrent shutdown, thermal shutdown, UVLO), the brake engages at the next status read (up to 5 ms) and `/error/command BrakeEngagedOnHiZ motorID` is sent. The brake stayed released. The servo mode is also cancelled (`ServoModeCancelledOnHiZ`, below).
  - `/resetMotorDriver` is accepted only while the brake is engaged or after `/free` (motor HiZ); otherwise it replies `CommandIgnored`. It made the driver HiZ with the brake released.
  - `/enableElectromagnetBrake` changes the setting only while the driver is HiZ, and disables the brake only while it is engaged or after `/free`; otherwise it replies `CommandIgnored`. Sending the current value does nothing. After a change the brake output is engaged and the state is engaged. Before, disabling a released brake engaged it on a turning motor, and enabling it on an energized motor left a state where `/activate 0` and `/hardHiZ` did nothing. The same rule applies to a config loaded over USB serial (a warning is printed for a motor that is not changed).
  - `/setBrakeTransitionDuration` with a value outside 0-65535 replies `CommandIgnored` and keeps the setting. The value wrapped around.
  - `/resetDevice` and the USB serial command `R` (used by the config tool to reboot) first stop the turning motors with a hard stop, engage their brakes and wait for the longest `brakeTransitionDuration` of them (at most 1 s), then restart. `R` replies `{"result":"ok","message":"Rebooting..."}` before this wait. Before, the board restarted at once. The MCU reset puts the drivers in standby (HiZ) at once (their reset input floats and is pulled down inside), while the STEP800 brake outputs kept their released state until `setup()` (about 0.5 s; STEP400: the pins float and the Brake Board pull-downs engage the brakes, without the transition time).
  - When the watchdog detects a hang (see the watchdog time below), every brake output is engaged first, then the firmware waits for the longest `brakeTransitionDuration` of the motors with the brake enabled and not engaged (at most 1 s) before the watchdog resets the board. The reset therefore comes up to 1 s later than before; the reset cause in `/booted` is still `4`. No hard stop is sent at this point. Before, the brakes stayed released after the watchdog reset as above.
  - KVAL_HOLD (TVAL_HOLD in current mode) is raised to at least half of KVAL_RUN (TVAL_RUN) whenever a motor with the brake enabled is energized again: `/activate 1` from engaged or engaging (as before), and now also after `/free` (`/activate 1` or a motion command). After `/free` the motor was energized with the configured holding value.
  - Homing at startup (`homingAtStartup`) with the brake enabled first releases the brake as `/activate 1` does, and starts the homing once the brake is released. It failed because the brake was engaged, and the goUntil timeout later sent a hard stop to the HiZ motor.
  - `/activate 1` no longer toggles the LED (debug code).
- `/goTo`, `/goHome`, `/goMark` (and `/combine/goTo`) judge their direction correctly when the home switch or the limit switch prohibits a motion (`/setProhibitMotionOnHomeSw`, `/setProhibitMotionOnLimitSw`). The direction was reversed for a target less than 2048 steps away (so a short move away from the switch was refused with `HomeSwActivating` / `LimitSwActivating` and a short move towards it was started), and wrong again beyond 2^21 steps. It is now the sign of the 22-bit difference to the target, the way the driver goes (the shortest way).
- Settings made with a Raw command are kept as settings: `/setSpeedProfileRaw`, `/setMaxSpeedRaw`, `/setMinSpeedRaw`, `/setFullstepSpeedRaw`, `/setAccRaw`, `/setDecRaw` now also set the acceleration, deceleration, maximum, minimum and full-step speed that `/saveConfig` saves and `/resetMotorDriver` (also the reset after a fault) applies again. They changed the register only, so a reset or a saved configuration brought back the value from before. The value kept is the one the register converts back to the same Raw value, so the register is the same after `/resetMotorDriver` (it can differ from `/getMinSpeed` and `/getFullstepSpeed` by half a register step, below what the register resolves). `/setMinSpeedRaw` ignores bit 12 (it switched the low speed optimization on without `/enableLowSpeedOptimize`); while the optimization is on it only changes the saved value, as `/setMinSpeed` does.
- `/setStallThreshold` also changes the saved STALL_TH (`/saveConfig`, `/resetMotorDriver`). It changed the register only.
- `/setPositionReportInterval` for one motor also clears the position list report interval that is saved, as it did for 255. A configuration saved after switching from the list to one motor's report started the list report again at the next start and cleared the motor's report.
- `/setDecayModeParam` (STEP400): TON_MIN and TOFF_MIN are 0-127 (7 bit); a value outside it replies `CommandIgnored` and applies nothing. 128-255 were taken modulo 128 by the driver while the saved value stayed 128-255. T_FAST is 0-255 as before.
- `/getKval`, `/getTval` and `/getTval_mA` (STEP400) return the settings (what `/setKval` and `/setTval` set and `/saveConfig` saves) instead of the registers. In the current mode the KVAL registers keep the value from before, and in the voltage mode the TVAL registers do (`/setKval` changes the registers only in the voltage mode, `/setTval` only in the current mode; the other set is applied by `/setVoltageMode` / `/setCurrentMode`). The KVAL_HOLD (TVAL_HOLD) raised for a motor with the brake is returned too. On the STEP800 the answer is the same as before.
- `/goUntilRaw` limits the speed to 20 bits (the driver libraries do so too).
- A command that writes a driver register that can be written only in some states (the register map of the L6470 and PowerSTEP01) replies with an error and applies nothing to a motor that is not in that state. The driver ignored the write and flagged it as not performed, so `/error/command CommandIgnored motorID` was sent, but the firmware variable and the saved configuration took the new value anyway, so the register (what the get commands return) and the saved value differed. Now the state is read from the driver when the command arrives, and the dedicated error is replied (`MotorNotHiZ` / `MotorNotStopped`) with nothing applied. With 255 each motor is judged alone: motors in the state are changed, the others reply with the error.
  - `/error/command MotorNotHiZ motorID`: the outputs must be HiZ (registers writable only in HiZ). `/setMicrostepMode`, `/setHomeSwMode` (SW_MODE of CONFIG), `/setBemfParam` (INT_SPEED, ST_SLP, FN_SLP_ACC, FN_SLP_DEC), `/setDecayModeParam`, `/setVoltageMode` and `/setCurrentMode` (STEP400). A motor holding its position is not HiZ: send `/softHiZ` or `/hardHiZ` first.
  - `/error/command MotorNotStopped motorID`: the motor must be stopped or HiZ (registers writable only when stopped). `/setAcc`, `/setDec`, `/setMinSpeed`, `/setSpeedProfile` (ACC and DEC; MAX_SPEED alone is writable always, but nothing is written to a motor that replies with the error), `/enableLowSpeedOptimize`, `/setLowSpeedOptimizeThreshold` while the optimization is enabled, and the Raw versions `/setAccRaw`, `/setDecRaw`, `/setMinSpeedRaw`, `/setSpeedProfileRaw`. A motor that is turning kept its old value, now with the error; a motor that is stopped (also while holding) is changed.
  - `/setVoltageMode` and `/setCurrentMode` change the mode only if the driver took it (STEP_MODE is read back). The driver flagged the write as not performed (`CommandIgnored`), but the stored mode was changed while the driver kept the old one, so `/setKval` and `/setTval` then wrote the wrong registers.
  - `/setMicrostepMode` on a STEP400 motor in current mode replies `CommandIgnored` for a step mode finer than 1/16 (the PowerSTEP01 current mode goes up to 1/16).
- OSC arguments are checked before a command is applied (all commands, STEP400 and STEP800). A command with too few arguments replies `/error/osc MissingArgument`; an argument of the wrong type (a string for a number, `/setConfigName` with a non-string, NaN or infinity) replies `/error/osc WrongDataType`; nothing is applied either way. They were applied as 0: `/setKval 1` set every KVAL of motor 1 to 0, `/setSpeedProfile 1` set acc, dec and max speed to 0, and the positions missing in `/setTargetPositionList` became 0 (a servo-mode motor ran to 0). Arguments beyond the ones a command needs are still ignored. A motor ID outside 0-255 replies `/error/command MotorIdNotMatch motorID` with the value sent; 257 and 511 were read as 1 and 255.
- A value outside the range of a command is rejected with `/error/command CommandIgnored motorID` (255 for `/setPositionListReportInterval`) and nothing is applied: `/setPositionReportInterval` and `/setPositionListReportInterval` above 65535 (32768 and above were read as negative and disabled the report; a negative interval still disables it), `/setGoUntilTimeout` and `/setReleaseSwTimeout` below 0 (they became about 49 days), `/setElPos` with a full step outside 0-3 or a microstep outside 0-127 (they were clamped), `/setServoParam` with a negative gain (it was set to 0).
- `/releaseSw` reads its action argument like the other boolean arguments (a number of 1.0 or more, or a positive integer, is true). It read it as an integer, so 0.5 was 0.
- USB serial diagnostic command `b` (brake output test) is available only in test builds (`HIL_PROBE`). It switched the brake outputs regardless of the brake state.
- Stop and HiZ commands cancel pending motion, **also for motors with the brake disabled**: `/softStop`, `/hardStop`, `/softHiZ`, `/hardHiZ`, `/activate 0`, `/free`, `/enableServoMode` (both), `/resetMotorDriver`, and the automatic brake engage cancel
  - a `/goTo`, `/goToDir`, `/goHome` or `/goMark` waiting for the BUSY flag to clear. It was sent when the motor became not busy, so a stopped motor started again.
  - the homing, also the state left by a `/goUntil` or `/releaseSw` sent directly: its timeout sent a hard stop, which energized a motor made HiZ in the meantime. `/homingStatus` is reported as before (only for `/homing`).
  - the servo mode.
  An accepted motion command also cancels a `/goTo` (etc.) waiting for BUSY, so the waiting command no longer overrides it later.
- The automatic hard stops are not sent to a motor whose driver is HiZ, **also with the brake disabled**: home switch with `/setProhibitMotionOnHomeSw`, limit switch (STEP400, `SW_HARD_STOP`), switch event in the servo mode, and the goUntil / releaseSw timeouts (the timeout error is still sent). A hard stop energizes a HiZ driver.
- A motion command (e.g. `/run`) that clears the homing state now also clears the state of a `/goUntil` sent directly.
- Boolean values that were sent with the OSC type tags `T` / `F` are now sent as integers `0` / `1` (type tag `i`), as intended for all STEP series messages. Clients that expect `T` / `F` for these arguments must be updated:
  - `/uvlo motorID state`: the report sent when the UVLO state changes (enabled by `/enableUvloReport`). The reply to `/getUvlo` already used `i`.
  - `/lowSpeedOptimizeThreshold motorID threshold enabled`: the third argument (`enabled`), reply to `/getLowSpeedOptimizeThreshold`.
- `/booted` has a second argument, `resetCause` (`i`): `/booted myId resetCause`. Clients that check the exact number of arguments are affected. The numbers are part of the specification; new causes will only be added as 7, 8, ... Clients that accept only the known numbers must also accept `6` (added in this release) and treat an unknown number as "other".

  | Value | Reset cause |
  |---|---|
  | 0 | Unknown |
  | 1 | Power-on |
  | 2 | Brown-out (supply voltage drop) |
  | 3 | Reset pin |
  | 4 | Watchdog |
  | 5 | Software reset (e.g. after firmware upload over USB) |
  | 6 | CPU fault: the reset after a CPU exception (HardFault on the SAMD21), see Fixed |

  If several causes are flagged, the first of CPU fault, brown-out, power-on, watchdog, reset pin, software is reported. After a power-on or a brown-out the CPU fault is never reported (the RAM that marks it is not kept), so a fault followed by a power cycle reports `1` or `2`. The MCU itself reports the reset after a CPU fault as a software reset (`resetCauseRaw` in `T`), or as a watchdog reset if the fault handler hangs.

  The number is the reset cause reported by the MCU, as is. On the SAMD21 (current STEP400 and STEP800), the brown-out detector (BOD33) holds the reset while the supply rises, so a normal power-up is often reported as `2`. Treat both `1` and `2` as a reset by the power supply. With another MCU in the future, the same operation may report a different number (the meaning of each number does not change).
- Watchdog time: a hang is detected about 250 ms after the last watchdog reset (256 cycles of the watchdog clock), the watchdog period is about 500 ms (512 cycles). v2.1.0 reset the board about 62.5 ms after a hang, without an early warning; the development versions before this release used 2 s and 4 s. The clock is the internal ultra-low-power oscillator (OSCULP32K / 32, nominally 1024 Hz), so the actual times vary with the chip, the supply and the temperature (measured on the bench: 243-247 ms from the hang to the early warning). The longest interval between two watchdog resets in normal operation measured on STEP400 and STEP800 is 117.4 ms (STEP800, `/get* 255`, which sends 276 replies); the time is at least twice that and 100 ms more. Commands and loads that block longer would now restart the board; none is known. The config save to the SD card (USB serial `{`, `/saveConfig`) runs with the watchdog off, as before (measured up to 242 ms).
- Servo mode: the update period is 5 ms instead of 10 ms (STEP400, STEP800). This replaces the 10 ms +/- 0.7 ms period given under Fixed. The integral and derivative terms are scaled by the period, so the same `kP`, `kI` and `kD` were designed to give about the same response; with the shorter period the response can still differ, so retune the gains if needed. Measured on STEP800 with all motors in the servo mode, `/setTargetPositionList` at 100 Hz and position reports every 0, 10 or 20 ms (or `/setPositionListReportInterval` 20 ms): 5 ms +/- 0.7 ms (4.31 to 5.70 ms). An OSC message that sends several replies (e.g. `/getPosition 255`, about 2.7 ms) delays the next update by up to its length (measured up to 7.75 ms between two updates).
- The status of the drivers is read every 5 ms instead of every 10 ms, and the brake, the limit switches (STEP400), the homing timeouts (`goUntilTimeout`, `releaseSwTimeout`) and the servo update run with it. Status reports (`/busy`, `/HiZ`, `/homeSw`, `/dir`, `/motorStatus`, `/swEvent`, `/uvlo`, `/thermalStatus`, `/limitSw`) arrive up to 5 ms earlier; they are still sent only on a change. (`/overCurrent` and `/stall`: see below.) The brake times are in 5 ms steps: the release after `/activate 1` comes 0-5 ms after `brakeTransitionDuration` (measured 99.8-105.4 ms for 100 ms; before 99.8-107.6 ms), and the engage after a stop or a HiZ is judged at the next status read. Position reports, the DIP switch read, the Tx/Rx LEDs, the boot message and the watchdog still run every 10 ms, and the position report intervals are as accurate as before (measured on STEP800: 19.3 to 20.7 ms for 20 ms, 9.3 to 10.7 ms for 10 ms).
- `/overCurrent` and `/stall` are sent at once when the condition starts and then, while it lasts, at most every 200 ms per motor and kind. Before, they were sent at every status read while the condition lasted (every 10 ms; every 5 ms with the 5 ms status read). Detections within the 200 ms are not lost: they give one message at the end of the interval. Detections while the report is disabled (`/enableOverCurrentReport`, `/enableStallReport`) are not sent later. The messages are unchanged.
- `/getStatus` (one motor and `255`) and `/getStatusList` read the STATUS register with GetParam instead of GetStatus, so they no longer clear the latched flags of the driver (e.g. OCD, the stall flags, UVLO, SW_EVN). The values are the same register as before. Clearing them kept the status poll from seeing a flag, so the matching report (`/overCurrent`, `/stall`, `/swEvent`, ...) could be lost. Only the status poll (every 5 ms) clears the flags now: a `/getStatus` or `/getStatusList` sent right after another can still show a flag that the earlier reply showed (until the next poll, up to 5 ms). The recovery of a driver after an overcurrent shutdown is unchanged (the poll clears the flag as before).
- When a driver goes HiZ by itself (overcurrent shutdown, thermal shutdown, UVLO) in the servo mode, the servo mode is cancelled and `/error/command ServoModeCancelledOnHiZ motorID` is sent (follows `/reportError`), with or without the electromagnetic brake. Nothing is sent to the driver. With the brake enabled, `BrakeEngagedOnHiZ` is also sent. The commands that make the driver HiZ (`/softHiZ`, `/hardHiZ`, `/activate 0`, `/free`, `/resetMotorDriver`, also for all motors and `/combine/...`) cancel the servo mode first and do not send this error. Enable the servo mode again with `/enableServoMode 1` (the current position becomes the target).
- Enabling the servo mode (`/enableServoMode`) resets the integral and the previous error of the PID controller. The previous values were kept from the last time the servo mode was used.
- The servo mode position error is wrapped correctly around the ends of the ABS_POS range (the wrap was off by one step).
- Servo mode (STEP400): the home switch and the limit switch are judged separately. A pressed home switch stops the motion towards `homingDirection` (with `/setProhibitMotionOnHomeSw` or the home switch in the hard stop mode), and a pressed limit switch stops the motion away from it (with `/setProhibitMotionOnLimitSw` or the limit switch in the hard stop mode), as before. While the home switch was pressed, the limit switch was not checked. Only a motor with both switches pressed behaves differently.
- `/goUntilRaw 255 ...` (all motors) interprets the speed as a raw register value, like `/goUntilRaw` for a single motor. It was treated as steps/s.
- `/getDir 255` (all motors) returns the direction. It returned the HiZ state.
- `/getMinSpeed` returns `0.0` for a motor with low speed optimization enabled. While it is enabled, the MIN_SPEED register of the driver holds the optimization threshold (get it with `/getLowSpeedOptimizeThreshold`) and the actual minimum speed is 0. For a motor with low speed optimization disabled, it returns the MIN_SPEED register value of the driver in steps/s. A single motor and all motors (`255`) now behave the same:
  - Single motor: returned the MIN_SPEED register value (the threshold) while low speed optimization was enabled.
  - All motors (`255`): returned the stored minimum speed setting.
- `/setMinSpeed 255` (all motors) checks the low speed optimization setting of each motor. It read an invalid array element.
- `/hardHiZ` for a single motor no longer sends a soft stop before the hard HiZ; single motor, all motors (`255`) and `/combine/hardHiZ` behave the same. For a motor with the electromagnetic brake enabled and released (`/activate` done), the motor is stopped with a hard stop (still energized) before the brake is engaged, so it does not keep running during the brake transition time. While the brake is engaged or engaging, the command does nothing as before.
- `/goUntil` and `/goUntilRaw` report an activated home switch as `/error/command HomeSwActivating motorID`, the text in the error list. It was sent as `HomeSwActivated`. It now follows `/reportError` like the other command errors, so it is not sent while error reports are disabled.
- `/goUntil`, `/goUntilRaw` and `/releaseSw` for a motor in the servo mode reply `/error/command InServoMode motorID` and do nothing, like the other motion commands and `/homing`. They were sent to the driver. With `255`, only the motors in the servo mode reply the error; the others execute the command.
- Received address patterns: in some corner cases where the CNMAT implementation read past the end of the pattern (e.g. characters following a `{...}` list), the match result can differ from before.
- The W5500 retransmission time is set to 20 ms and the retry count to 2. A send to a destination that does not answer ARP blocks for about 41 ms (measured on STEP800) instead of 1.6 s or more with the defaults (200 ms, 8 retries).
- When a send to the destination fails (a destination that has never answered ARP, e.g. a wrong destination address), the sends to that destination are paused for 1 s: the messages in that time are dropped, not sent later. After 1 s, the next message is sent as a single retry; if it fails, the sends are paused for another 1 s. A packet received from that destination resumes the sends at once. Broadcasts (`/booted`) are not affected. Before, every message to such a destination stopped the processing for about 41 ms, so with the per-motor position reports enabled the board almost stopped (the loop blocked up to 327 ms every 10 ms). A destination that answered ARP once and then left the network does not make the sends fail: the W5500 keeps sending to the resolved MAC address (measured for 5 minutes), so the sends are not paused and do not block (see the resolution of the MAC address below for a client replaced by another device). USB serial prints one line when the sends are paused and one when they are resumed; `p` counts the failed sends and the dropped messages.
- Resolution of the MAC address of the destination: the board resolves the MAC address of `destIp` again (1) on `/setDestIp` from another address than the current `destIp`, before `destIp` was set (`isDestIpSet` false), or 1.5 s or more after the last packet from `destIp` (a client replaced by another device takes longer than that); also after a resolution that gave up, until a send to `destIp` goes out; a `/setDestIp` within 1.5 s of the last packet from the same address (e.g. every second as a heartbeat) does not; (2) once `destIp` is set (`canSendMsgBeforeDestIp`, or after `/setDestIp`): at the start and after a change of the ID (DIP switch) while running, once the Ethernet link has been up for 1 s (as `/booted`), and when the link comes up again after it was down (with a direct cable, also a PC replaced without `/setDestIp`; not through a switch). The board then sends one byte of UDP to port 9 (discard) of 255.255.255.255, then one byte of UDP to port 9 of `destIp` (a probe) at once and every 150 ms until one goes out (the client answered the ARP request in time) or 2 s have passed. Two probes are always at least 150 ms apart, also when `/setDestIp` keeps coming. While the link is down no probe is sent and the 2 s do not run. Meanwhile the messages to `destIp` (replies, reports, errors) are dropped, not sent later; broadcasts (`/booted`) are sent. The reply to a `/setDestIp` that starts the resolution (`/destIp`) is sent once the MAC address is resolved, so it can come later than before (up to 2 s); after the 2 s it is tried once more, and the sends are then paused as after a failed send (above). Another `/setDestIp` during the resolution replaces the held `/destIp` (one `/destIp` for both) and, if it starts a resolution itself, restarts the 2 s. A `/setDestIp` that starts none is answered at once (or, during a resolution, when it ends). Each probe that fails blocks the processing for about 41 ms (as one failed send). The client receives the probes (UDP to port 9; a Mac answers each with ICMP port unreachable, which has no effect on the board). Measured on STEP400_R1: a wired client is resolved by the first probe, `/destIp` 3-13 ms after `/setDestIp`; a Mac on Wi-Fi (through the access point) needed 1-8 probes, `/destIp` 25-1290 ms after `/setDestIp` (20 of 20 resolved), and 0.5-1.3 s of position reports (20 ms) were dropped meanwhile; after the link came back, the resolution started about 1 s later and the reports resumed after the first probe; for an unreachable destination, 13 probes in 2 s blocked the loop up to 41 ms each (no watchdog warning). Send `/setDestIp` at the start of the connection and after a change of the network or of the PC (another PC or network adapter with the same IP address, Wi-Fi and wired switched; at least 1.5 s after the last packet of the old one): without it the board keeps sending to the old MAC address (except when the link went down, see above). If `/destIp` does not come, send `/setDestIp` again. To check that the board is alive, use a command with a reply such as `/getVersion`, not `/setDestIp`. USB serial prints `Ethernet link up` / `Ethernet link down` when the link changes. `p` counts the resolutions (`arpResolve`), the probes (`arpProbe`, of these failed `arpProbeFailed`), the resolutions ended by a probe (`arpResolved`) or given up (`arpTimeout`), the held `/destIp` sent (`arpDestIpSent`) and the messages dropped during a resolution (`arpDropped`).
- Inherited from driver libraries v1.2.0:
  - The acceleration and deceleration reported by `/getSpeedProfile` are about 4.9% smaller; they now match the datasheet.
  - `/setAcc`, `/setDec` and `/setSpeedProfile` round to the nearest register value, so the written value can differ by 1 LSB.
  - STEP400: the default slew rate setting is now the designed value, so the switching is faster.
  - STEP400: a maximum speed of 0 is written as 1 (the register value 0 is reserved) by `/setMaxSpeed`, `/setSpeedProfile` and the `maxSpeed` setting of the config file. `/setMaxSpeedRaw 0` still writes 0. STEP800 is unchanged.
  - STEP400: `/setFullstepSpeed` and `/setFullstepSpeedRaw` keep the BOOST_MODE bit of the FS_SPD register. They cleared it before. The firmware does not set BOOST_MODE, so this is not visible unless the bit is set by other means.
  - `/goUntilRaw` clamps the speed to 20 bits (`0xFFFFF`), like `/runRaw`. Larger values were sent as is, and the driver ignored the upper bits.

### Changed

- STEP800: the brake outputs change as soon as the brake state changes (0.2-0.3 ms after the command on the HIL bench). They were sent with the next DIP switch read and appeared at the read after it, 10-20 ms after the command, so the brake and motor overlapped for less than `brakeTransitionDuration` (about 89 ms instead of 100 ms).
- The brake outputs are engaged first in `setup()`, before the drivers are reset, for a restart that did not engage them (reset button, brown-out). STEP400: the pins are driven low. STEP800: the cleared shift register is latched into the 74HC595, whose outputs otherwise keep their state through an MCU reset. At power-up the STEP800 outputs are still released until then (about 250 ms, mostly the bootloader).
- The watchdog is driven by the firmware (`src/watchdog.cpp`) instead of the Adafruit SleepyDog library, whose interrupt handler cannot be replaced: same clock, early warning interrupt about 250 ms after the last reset, watchdog period about 500 ms (see the watchdog time under Behavior changes).
- In every 5 ms slot of the main loop, the status of the drivers is read first; the brake, the limit switches (STEP400), the homing timeouts and the servo update use this status. The slots are scheduled on `micros()`.
- OSC messages are received with a single read into a static buffer and dispatched by a table lookup instead of about 140 sequential address comparisons. Patterns in received addresses (e.g. `/enable*Report`, `/set{Acc,Dec}`) and addresses followed by `/...` keep working as before.
- OSC messages are encoded into a static buffer and sent with a single write, without heap allocation.
- Status and position reads of all drivers (servo mode, status polling, position reports, `/getPositionList`, `/getStatusList`, `/getPosition 255`, `/getStatus 255`) use one packed daisy-chain transfer instead of one transfer per driver. Requires driver libraries v1.2.0.
- STEP400: the limit switch inputs, read with the ADC of the drivers, are polled with one packed daisy-chain transfer instead of one transfer per driver.
- Received packets larger than 512 bytes, and messages with more than 16 arguments, are answered with `/error/osc OscSyntaxError`.
- The CNMAT OSC library is no longer used.
- USB serial: the status JSON (`T`) includes `mcu`, `resetCause` and `resetCauseRaw` in the `board` object.

### Added

- USB serial: the destination MAC address, the MAC address the last send went to: `Destination MAC address` in `s`, `destMac` (6 integers) in the `board` object of `T`. It is the address the W5500 resolved for `destIp`, ff:ff:ff:ff:ff:ff (255 x 6) after a broadcast (`/booted`, the start of a resolution) until the next send to `destIp`, and 0 x 6 if the UDP socket is not open. `arpPending` in the `board` object of `T`: true while the MAC address of `destIp` is being resolved.
- `/getBrakeStatus motorID` replies `/brakeStatus motorID state` (`i`, `i`); `255` for all motors. `state` is `-1` for a motor with the brake disabled, otherwise:

  | Value | State | Brake output | Driver |
  |---|---|---|---|
  | 0 | Engaged | engaged | HiZ |
  | 1 | Releasing (`/activate 1`, waiting `brakeTransitionDuration`) | engaged | energized |
  | 2 | Released | released | energized |
  | 3 | Stopping (`/softHiZ`, `/activate 0`: decelerating, engages when stopped) | released | energized |
  | 4 | Engaging (waiting `brakeTransitionDuration`, then HiZ) | engaged | energized |
  | 5 | Free (`/free`) | released | HiZ |

  The numbers are part of the specification; new states will only be added as 6, 7, ...
- Command errors `BrakeReleaseFailed`, `BrakeEngagedOnHiZ` and `ServoModeCancelledOnHiZ` (`/error/command`, follow `/reportError`).
- USB serial: the brake states are shown with their numbers and names (`s`). HIL_PROBE builds (for the HIL bench): `Z` sends HardHiZ to all drivers, bypassing the brake; `D` prints the driver registers read at boot before the reset; `Y` floats the driver reset line for 300 ms; `W` hangs for the watchdog.
- USB serial command `p`: prints timing statistics (loop, OSC receive, servo update, status check, servo interval, OSC messages dispatched by pattern matching or not matched, slots started a whole period or more late, position report clock realigned to `millis()`) and resets them.
- STEP800: timing probes on spare pins, enabled with the `HIL_PROBE` build flag (no effect on normal builds).
- `tools/hil/`: a hardware-in-the-loop test bench using Digilent Analog Discovery 2.

### Fixed

- CPU fault (HardFault): the firmware engages every brake output at once, waits for the longest `brakeTransitionDuration` of the motors with the brake enabled and not engaged (at most 1 s, the same wait as the watchdog), then restarts; `/booted` reports `resetCause` `6`. The handler runs from RAM and writes the brake outputs directly (STEP400: EM_1-EM_4 low; STEP800: the 74HC595 cleared and latched), without SPI and without a command to the drivers; the restart puts the drivers in standby. Before, a HardFault stopped the firmware with the brakes released and the drivers in their last state until the watchdog period (4 s in the development versions; v2.1.0 restarted after about 62.5 ms, with the STEP400 brakes engaged by the Brake Board pull-downs). If the fault handler itself fails, the watchdog period (about 500 ms) restarts the board (`resetCause` `4`). Measured on STEP400 with `brakeTransitionDuration` 100 / 1000 ms: brakes engaged within 0.1 ms of the fault, restart 100.1-100.2 / 1000.2-1000.5 ms later.
- STEP400 (STEP400_R1 board): unplugging the USB cable while the Ethernet cable is connected can cause a CPU fault (a hardware issue of this board, which also happens with v2.1.0; not seen on STEP800). The board now restarts as above with the brakes engaged (measured 5 of 5 unplugs: brakes engaged, restart 100 ms later, `resetCause` `6`). With the development versions it stopped for up to 4 s with the brakes released.

- `/homing`: the homing often ended with `/homingStatus` 4 and `/error/command ReleaseSwTimeout motorID` about 1 ms after the switch was found, instead of 3 (ReleaseSW completed). The status poll takes the time once at its start; when it finds the home switch, it starts ReleaseSW and records its start time with a new reading of the time, and if the millisecond counter advanced in between, the timeout check later in the same poll computed an elapsed time of -1 ms, which as an unsigned value (about 49.7 days) exceeded `releaseSwTimeout`. The same could happen to the goUntil timeout. Whether it happened depended on the start-up: in almost every homing or almost never, because the polls follow each other at exactly 5 ms and their phase against the 1 ms steps of the millisecond counter is set at each start-up. A start time later than the poll time now counts as 0 ms elapsed. Measured on STEP800 (HIL bench, check C4-2): failed in 10 of 11 runs before, passed in 8 of 8 after (and in 6 of 6 after the fix below). The same comparison of the poll time with a time taken later in the poll is fixed in two other places. The transition time of the electromagnetic brake (`brakeTransitionDuration`: from energizing the driver to releasing the brake, and from engaging the brake to making the driver HiZ): no current path starts it in a poll before the poll checks it, so this is fixed before it could happen; no difference is visible to OSC clients. The RX / TX LEDs: the position reports are sent in the poll before the LEDs are updated, so the TX LED blink they start was turned off at once whenever the millisecond counter had advanced since the start of the poll (found in the code: always when four or more motors report, as each send takes about 0.25 ms); it now stays on for 30 to 40 ms as for the other sends. A timeout of 2^31 ms or more (e.g. a negative `/setGoUntilTimeout` or `/setReleaseSwTimeout` argument) no longer fires; before, it fired after 24.8 days or more.
- A client replaced by another device with the same IP address (another PC, another USB-LAN adapter) received no reply and no report, although its commands worked, until the board was restarted: the W5500 keeps the MAC address it resolved by ARP and resolves it again only when a send goes to another IP address, and `/setDestIp` from the same address, a link change, or ARP and gratuitous ARP from the new device did not change it. Now `/setDestIp` from the new device, 1.5 s or more after the last packet from the old one, repairs it (the resolution of the MAC address, Behavior changes); its `/destIp` is the first message to the new device. With a direct cable the link change repairs it too. Not repaired when the new device, connected through a switch, sends only other commands: send `/setDestIp` (or restart the board).
- Servo mode: the update period alternated between about 7 and 13 ms (mean 10 ms) when position reports were enabled, because the servo update ran after the status poll, which is about 2.5 ms longer when it sends position reports (every other poll with `/setPositionReportInterval` 20 ms). The integral and derivative terms of the PID assume 10 ms, so the effective gains changed by about 25 % up and down from one update to the next. The servo update now runs at a fixed point of the status poll (after the status read, the brake, the limit switches and the homing timeout, before the position reports). Measured on STEP800 with all motors in the servo mode, `/setTargetPositionList` at 100 Hz and position reports every 0, 10 or 20 ms: the period is 10 ms +/- 0.7 ms (9.31 to 10.68 ms; before: 6.84 to 13.16 ms with reports every 20 ms). With the same gains, the response may change slightly because the period is now stable. OSC messages and arguments are unchanged. (The period is now 5 ms; see Behavior changes.)
- Servo mode with the electromagnetic brake disabled: when the driver went HiZ by itself (overcurrent shutdown, thermal shutdown, UVLO), the next servo update sent Run, which energized the driver again: an overcurrent shutdown could repeat (the status read clears the flag), and the motor could start moving to the target when the temperature or the motor supply came back. The servo mode is now cancelled (see `ServoModeCancelledOnHiZ` under Behavior changes).
- USB serial `F<filename>` (set the file name of the SD save) typed by hand, with characters more than the watchdog time apart, restarted the board: the wait for the characters (up to 2 s each) did not reset the watchdog. It now resets it, and the whole name is limited to 10 s (as `{`); the reply is an error after 10 s without a line end.
- USB serial `R`: the board waits at least 50 ms after the reply before it restarts, so the reply (`Rebooting...`) also arrives when there is no brake to wait for. It was often lost (the restart disconnects USB before the host has read it).
- With the DIP switch ID added to the IP address (`isMyIpAddId`), an address beyond .254 (ID 155 or more with the default 10.0.0.100) is no longer used: the ID is not added, the configured address is used and a warning is printed on USB serial. Before, the address became the broadcast address (.255) or wrapped around (.0 to .99). The same applies to the send port (`isOutPortAddId`) beyond 65535.
- Config received from the config tool (USB serial `{`): the IP address, send port and MAC address with the ID added were stored as the configured values (before the ID), so the ID was added twice after a later ID change. The received values are now stored as the configured values only, and the running address and port are not changed (applied by a reboot).
- USB serial diagnosis: the thermal status of the L6470 (STEP800) is shown with its own names (warning, shutdown); the `c` output showed `reportBUSY` and `reportOCD` twice and not `reportLimitSwStatus` (STEP400).
- `/resetDevice` caused a HardFault, and the device was actually restarted by the watchdog timeout. It now resets with `NVIC_SystemReset()`, and `/booted` reports the reset cause `5` (software).
- USB serial diagnosis: `EN_TQREG` of the CONFIG register was always shown as 0.
- USB serial diagnosis: the microstep of EL_POS and the fields of the CONFIG register (`OSC_SEL`, `EXT_CLK`, `SW_MODE`, `EN_VSCOMP`, `OC_SD`, `UVLOVAL`, `VCCVAL`, `POW_SR`, `TSW`, `PRED_EN`, `F_PWM_DEC`, `F_PWM_INT`) were extracted with `%` instead of a bit mask and were shown wrong.
- The command error texts were constructed on the heap in every source file that included `globals.h`.
- `/goTo`, `/goToDir`, `/goHome` and `/goMark` on a busy motor, and the USB serial command `s`, read the STATUS register with GetStatus, which clears the latched warning flags, so the status poll could miss them and the reports `/overCurrent`, `/stall`, `/swEvent`, `/uvlo` and so on were lost. They now read it with GetParam, which does not clear them.
